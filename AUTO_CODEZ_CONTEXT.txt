1. VISAO DO PRODUTO

O Auto CodeZ e um aplicativo desktop Electron para desenvolvimento de software com auxilio de IAs externas.

O Auto CodeZ e a interface principal. ChatGPT, Claude e Gemini sao mecanismos externos controlados por automacao de interface. O fluxo principal nao depende de API keys dessas IAs.

O usuario trabalha no projeto local dentro do Auto CodeZ. Ele envia um pedido, o aplicativo prepara o contexto, controla a IA escolhida, recebe a resposta, interpreta a proposta e apresenta alteracoes no editor para aprovacao.

2. PRINCIPIO CENTRAL

O usuario nao deve precisar trabalhar manualmente nas janelas externas das IAs.

Fluxo:

Usuario
-> Auto CodeZ
-> contexto do projeto
-> SessionManager
-> AiConnectorManager
-> conector do provider
-> automacao do navegador
-> IA externa
-> leitura da resposta
-> parser
-> proposta de alteracao
-> editor/diff
-> aceitar ou rejeitar
-> projeto local

A janela externa existe como mecanismo de execucao, nao como interface principal.

3. PROVIDERS

Providers atuais:

- ChatGPT
- Claude
- Gemini

Cada provider possui conector proprio, mas segue a mesma interface de alto nivel:

- disponibilidade
- preparacao
- localizacao da interface
- localizacao da aba
- localizacao do campo de mensagem
- envio
- leitura da resposta
- tratamento de erro

4. FLUXO CORRETO DA SESSAO

1. Usuario escolhe o provider.
2. Usuario escreve o pedido no Auto CodeZ.
3. Auto CodeZ monta o contexto relevante.
4. SessionManager cria e controla a AiSession.
5. AiConnectorManager seleciona o conector.
6. Conector procura uma aba valida do provider.
7. Se nao existir, abre a URL oficial.
8. O sistema espera a pagina carregar.
9. O sistema confirma a aba correta.
10. O sistema localiza especificamente o campo de composicao de mensagem.
11. Somente depois de confirmar esse campo o prompt pode ser colado.
12. O prompt e enviado.
13. A sessao entra em waiting.
14. O sistema aguarda uma resposta real.
15. O sistema detecta o fim da geracao.
16. O sistema le somente a resposta nova.
17. A sessao termina como completed, failed ou cancelled.
18. O parser interpreta a resposta.
19. O sistema cria propostas de alteracao.
20. O editor mostra diff e arquivos afetados.
21. O usuario aceita ou rejeita.
22. Somente alteracoes aceitas sao aplicadas.

5. REGRA CRITICA DE AUTOMACAO

Nunca usar o primeiro elemento editavel encontrado como campo de mensagem.

Nunca enviar Ctrl+V sem confirmar o elemento de mensagem.

Nunca usar a barra de endereco como fallback.

Nunca usar a barra de pesquisa do navegador como fallback.

Nunca usar a pesquisa interna da pagina como fallback.

Nunca focar uma janela aleatoria porque o titulo possui uma palavra parecida com o provider.

Se o campo correto nao for identificado, a sessao deve falhar de forma controlada e informar o motivo.

Um comportamento em que o prompt vai para a barra de pesquisa ou endereco e considerado falha critica.

6. INCIDENTES CONFIRMADOS

Durante os testes, Claude foi aberto, mas o prompt foi colado na barra de pesquisa. Isso confirmou que a estrategia generica de primeiro elemento editavel era insegura.

Tambem ocorreu uma situacao em que o VS Code foi trazido para frente quando Claude era o provider selecionado. Isso confirmou que fallback por titulo de janela e amplo demais.

Esses dois comportamentos nao devem voltar.

7. ABA E NAVEGADOR

URLs:

ChatGPT: https://chatgpt.com/
Claude: https://claude.ai/
Gemini: https://gemini.google.com/app

Prioridade:

1. Reutilizar aba existente do provider.
2. Se nao existir, abrir a URL correta.
3. Esperar a aba aparecer.
4. Confirmar a aba pelo provider.
5. Interagir somente com essa aba.

Nao abrir uma nova aba se uma aba valida do mesmo provider ja existir, salvo quando uma nova conversa for exigida explicitamente.

8. FOCO E SEGUNDO PLANO

O objetivo final e executar a automacao em segundo plano sempre que a tecnologia permitir.

Quando UI Automation exigir foco temporario, o foco deve atingir a interface correta e voltar ao Auto CodeZ assim que possivel.

Nao usar focusWindow de forma indiscriminada.

Nao usar findWindowHandleByTitle como fallback generico para decidir onde enviar texto.

9. LOCALIZACAO DO CAMPO DE MENSAGEM

A localizacao deve ser especifica por provider.

A estrategia deve analisar propriedades de acessibilidade do elemento, incluindo nome acessivel, tipo de controle, AutomationId, HelpText e tipo localizado.

Termos candidatos de acessibilidade:

ChatGPT:
- Message ChatGPT
- Send a message
- message
- prompt

Claude:
- Write a message
- Reply
- message
- prompt

Gemini:
- Enter a prompt here
- Enter a prompt
- prompt
- message

Esses termos sao evidencias de acessibilidade, nao garantias fixas. A implementacao deve validar a combinacao de propriedades e nunca aceitar qualquer Edit ou Document sem evidencia de ser o campo de composicao.

Elementos com evidencia de endereco, pesquisa, URL, omnibox ou navegacao devem ser rejeitados.

Se a arvore de acessibilidade nao fornecer evidencia suficiente, nao enviar.

10. ENVIO

Clipboard e permitido como meio de transferir o texto para o campo correto.

Clipboard nao substitui a identificacao do campo.

A ordem obrigatoria e:

localizar aba
-> selecionar aba
-> localizar campo especifico
-> focar campo especifico
-> confirmar foco
-> colar prompt
-> enviar

11. CONTEXTO DO PROJETO

O contexto enviado deve ser seletivo.

Prioridade:

1. pedido atual
2. arquivo ativo
3. arquivos diretamente relacionados
4. configuracoes relevantes
5. demais arquivos necessarios

Nao dominar o prompt com:

- .gradle
- .idea
- .kotlin
- caches
- binarios
- logs
- artefatos de build
- arquivos temporarios
- dependencias geradas

Respeitar .gitignore e regras proprias de exclusao de contexto.

12. PROMPT BASE

O prompt base deve orientar a IA a preservar comportamento existente, alterar somente o necessario, considerar dependencias, seguir padroes do projeto, nao inventar APIs sem necessidade, identificar todos os arquivos afetados e retornar uma resposta processavel pelo Auto CodeZ.

O prompt base deve permanecer separado da automacao.

13. SESSIONMANAGER

O SessionManager coordena o ciclo de vida.

Estados conceituais:

- created
- preparing
- sending
- waiting
- reading
- completed
- failed
- cancelled

Uma Promise executada em segundo plano nunca deve gerar UnhandledPromiseRejection.

Uma sessao antiga presa em waiting deve terminar, falhar ou ser cancelada de forma controlada.

Nao mascarar o problema permitindo concorrencia no mesmo navegador sem arquitetura explicita.

14. LEITURA DA RESPOSTA

A confirmacao de envio nao e a resposta final.

O leitor deve distinguir:

- conteudo anterior
- prompt enviado
- resposta nova
- botoes
- controles de navegacao
- mensagens antigas

O baseline anterior ao envio e uma estrategia inicial. O leitor deve evoluir para estrategias especificas por provider quando a acessibilidade permitir.

15. PARSER

A resposta deve ser convertida em uma estrutura de proposta.

Identificar:

- explicacao
- arquivos afetados
- caminho
- operacao
- conteudo novo ou patch
- criacao
- alteracao
- exclusao
- dependencias

Nao aplicar a resposta diretamente ao disco.

16. PROPOSTAS

Cada proposta deve possuir:

- caminho
- tipo de operacao
- conteudo ou patch
- estado
- provider de origem

Estados conceituais:

- pending
- accepted
- rejected
- applied
- failed

17. MULTIPLOS ARQUIVOS

Antes de aplicar qualquer parte, identificar o conjunto de arquivos afetados.

Validar caminhos, existencia, conteudo original e dependencias.

Evitar aplicar uma parte de uma mudanca que dependa obrigatoriamente de outra parte sem deixar isso claro.

18. SEGURANCA DE ESCRITA

A IA nao recebe permissao implicita para alterar qualquer arquivo do computador.

Caminhos devem permanecer dentro da raiz do projeto selecionado.

Nao aceitar caminho absoluto arbitrario para fora do projeto.

Antes de aplicar:

- validar caminho
- validar operacao
- validar conteudo original esperado
- verificar conflito com alteracoes locais
- verificar dependencias

19. INTERFACE

A interface segue a organizacao de um editor moderno, inspirada no VS Code.

Elementos:

- barra lateral
- arvore de arquivos
- editor central Monaco
- area de IA integrada

- propostas

A marca deve ser discreta.

A nova aba de IA e parte do plano, mas o acabamento final depende da estabilizacao do pipeline externo.

21. ESTADO ATUAL DA AUTOMACAO

browser.ts possui deteccao de abas via UI Automation do Windows.

Existe waitForAiTab para aguardar a aba aparecer.

Existe selecao da aba.

A antiga funcao generica de primeiro elemento Edit ou Document nao deve ser usada para enviar prompts.

Agora existe focusBrowserMessageInput(tab, provider), que exige evidencia especifica do campo de mensagem do provider e rejeita elementos associados a endereco, pesquisa, URL, omnibox ou navegacao.

Os conectores ChatGPT, Claude e Gemini devem usar essa funcao antes de qualquer Ctrl+V.

27. DECISAO ATUAL DESTA TAREFA

Data: 2026-08-29

O usuario determinou que AUTO_CODEZ_CONTEXT.txt deve ser atualizado sempre que houver algo novo no projeto.

O foco atual e corrigir a automacao do campo de mensagem dos providers.

O incidente mais recente foi Claude receber o prompt na barra de pesquisa do navegador. A causa foi uma estrategia generica de foco.

Tambem foi confirmado que trazer VS Code para frente durante uma operacao destinada ao Claude e comportamento incorreto.

A solucao desta etapa substitui o foco generico por uma busca especifica do campo de mensagem baseada em propriedades de acessibilidade e termos por provider.

Nenhum prompt deve ser enviado enquanto o sistema nao tiver identificado de forma confiavel a aba e o campo de mensagem do provider selecionado.

O proximo teste deve validar os tres providers, inclusive com outras abas e janelas abertas. Se o campo nao for identificado, o comportamento correto e falhar de forma segura, nunca colar em outro campo.
