AUTO CODEZ — DOCUMENTO DE CONTEXTO PERMANENTE
Última atualização: 01/09/2026

============================================================
1. PRODUTO E OBJETIVO
============================================================

Auto CodeZ é um aplicativo desktop real em Electron + Vite + TypeScript. É uma plataforma de desenvolvimento assistida por múltiplos provedores de IA, com interface própria, execução de ferramentas controladas, projetos locais, agente, chats, configurações, plugins futuros e conta/sincronização.

A arquitetura antiga baseada em automação de navegador/UI Automation para ChatGPT, Claude e Gemini não é mais o núcleo do produto. O fluxo principal é:

Auto CodeZ -> AI Runtime -> Provider Adapter -> API -> modelo.

O projeto deve ser tratado como software de produção: engenharia alta, código limpo, mudanças incrementais, validação antes de concluir mudanças, sem refatorações amplas desnecessárias.

20. NOVA ARQUITETURA CENTRAL: CONTA AUTO CODEZ
============================================================

A conta Auto CodeZ é uma das partes mais importantes do produto. Não é login cosmético.

A conta deve sincronizar praticamente todo o estado pertencente ao usuário, permitindo instalar o Auto CodeZ em outro PC e recuperar o ambiente sem depender de um arquivo de backup que possa ser perdido.

Dados que pertencem ao usuário:
- API Keys
- chats
- histórico dos chats
- configurações
- preferências
- biblioteca
- projetos sincronizados
- backups
- integrações
- permissões externas
- dispositivos conectados
- demais dados persistentes do produto.

O aplicativo instalado em si é local-only; os dados do produto que forem sincronizáveis pertencem à conta.

============================================================
21. USUÁRIO VS DISPOSITIVO
============================================================

Não existe “dispositivo rei”. O primeiro dispositivo conectado não tem autoridade superior.

Uma conta pode ter vários dispositivos com acesso equivalente aos dados sincronizados.

Exemplo:
Conta -> PC, Notebook, Laptop, etc.

Recursos físicos continuam locais ao dispositivo:
- filesystem local
- processos
- terminal
- hardware
- aplicativos instalados
- pastas explicitamente não sincronizadas.

Um dispositivo remoto não ganha automaticamente controle físico sobre outro computador.

============================================================
23. LOCAL-FIRST / OFFLINE
============================================================

Decisão arquitetural permanente:

AUTO CODEZ = LOCAL-FIRST + CLOUD SYNC + OFFLINE QUEUE.

Se a internet cair durante uma sessão:
- a sessão não é perdida;
- chats continuam acessíveis;
- histórico continua acessível;
- contexto local continua disponível;
- projetos locais continuam disponíveis;
- configurações continuam disponíveis;
- alterações continuam sendo salvas localmente;
- operações que dependem da cloud ficam pendentes;
- UI mostra estado de sincronização sem bloquear o usuário.

Quando a internet voltar:
- fila é processada;
- servidor confirma operações;
- alterações viram sincronizadas;
- conflitos são apresentados quando necessário.

REGRA FUNDAMENTAL: nunca apagar uma alteração local porque a sincronização falhou.

Fluxo:
alteração local -> salvar localmente -> fila -> tentar sync -> confirmação -> sincronizado.

Falha = salvo localmente + pendente.

O contexto da conversa atual deve permanecer local enquanto a sessão estiver aberta. A cloud é persistência compartilhada entre dispositivos, não a única fonte de contexto durante uma sessão.

============================================================
24. CONFLITOS ENTRE DISPOSITIVOS
============================================================

Conflitos importantes não devem ser resolvidos silenciosamente por “última escrita vence”.

Se dois dispositivos alterarem o mesmo recurso de forma conflitante, deve existir uma Solicitação de Alteração.

A notificação deve permitir:
- identificar dispositivo de origem;
- visualizar o que mudou;
- ver diff quando aplicável;
- aceitar;
- rejeitar;
- revisar novamente.

Se uma alteração antiga for aceita depois de outra já ter sido aceita, mostrar confirmação explícita, por exemplo:

“Você tem certeza que deseja aceitar esta alteração? O dispositivo {dispositivo} já fez uma alteração neste arquivo.”

O sistema precisa preservar revision/deviceId/timestamp/operação suficientes para detectar isso.

27. LOGIN / IDENTIDADES VINCULADAS / RECUPERAÇÃO
============================================================

A autenticação do Auto CodeZ é passwordless-first.

Métodos adotados como núcleo:
- Google
- GitHub
- Microsoft
- Passkeys

Acesso por e-mail, quando necessário, usa Magic Link temporário e não senha.

Telefone/OTP não faz parte da arquitetura planejada.
E-mail + senha não faz parte da arquitetura planejada.

A conta Auto CodeZ é independente das identidades externas. Um usuário pode vincular várias identidades à mesma conta, por exemplo:

Auto CodeZ Account
├── Google
├── GitHub
├── Microsoft
├── Passkey(s)
└── Magic Link / e-mail

Essas identidades não criam contas Auto CodeZ separadas. São diferentes mecanismos para autenticar a mesma conta.

A aba Perfil da interface principal é o local dedicado ao gerenciamento de identidade:
- perfil do usuário;
- e-mail principal;
- contas Google vinculadas;
- contas GitHub vinculadas;
- contas Microsoft vinculadas;
- Passkeys;
- acesso por Magic Link;
- vincular nova identidade;
- desvincular identidade, respeitando a regra de que a conta não pode ficar sem nenhum método de recuperação/acesso válido.

Segurança permanece separada e concentra:
- dispositivos conectados;
- sessões;
- revogação;
- atividade de autenticação;
- proteções de segurança.

Sincronização permanece separada e concentra:
- estado da sincronização;
- pendências;
- conflitos;
- solicitações de alteração.

Google, GitHub e Microsoft são responsáveis pela recuperação de suas respectivas identidades externas. Para Magic Link, o e-mail funciona como prova temporária de acesso.

Não existe fluxo planejado de recuperação por senha, pois senha não é parte do modelo principal.

Qualquer recuperação excepcional da conta deve possuir controles de segurança, auditoria e verificação adequada. Suporte manual, se necessário, deve ser posterior ao fluxo automático e nunca baseado apenas em informações facilmente falsificáveis.

37. CHECKLIST PARA NOVAS FUNCIONALIDADES
============================================================

Antes de implementar algo importante, perguntar:

1. Pertence ao usuário ou ao dispositivo?
2. Precisa funcionar offline?
3. Deve sincronizar?
4. É secret?
5. Pode gerar conflito entre dispositivos?
6. Precisa de permissão?
7. É local ou cloud?
8. Como recuperar o estado se falhar?
9. O que ocorre se a internet cair durante a operação?
10. O que ocorre se o provider estiver indisponível?

Nenhuma funcionalidade importante deve assumir internet, provider ou cloud sempre disponíveis.

============================================================
38. DIRETRIZ FINAL
============================================================

Auto CodeZ deve evoluir como uma plataforma real de desenvolvimento assistido por IA.

A prioridade é construir uma base coerente em que:
- IA seja provider-agnostic;
- execução seja segura;
- UI seja profissional;
- dados pertençam ao usuário;
- conta tenha funcionalidade real;
- múltiplos dispositivos tenham acesso equivalente aos dados;
- offline não destrua sessões/contexto;
- sincronização seja confiável;
- secrets sejam protegidos;
- conflitos sejam explícitos;
- plugins tenham permissões;
- e o produto continue sustentável conforme crescer.

Decisões futuras que alterarem arquitetura, UX, segurança, modelo de dados, roadmap ou comportamento fundamental devem atualizar este documento.
