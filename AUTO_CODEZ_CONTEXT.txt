AUTO CODEZ
DOCUMENTO DE CONTEXTO PERMANENTE DO PROJETO

ESTADO ATUAL

Em 29 de agosto de 2026 o conceito do Auto CodeZ foi redefinido. A automação de ChatGPT, Claude e Gemini por navegador deixa de ser o núcleo do produto. O projeto passa a ser uma plataforma desktop local-first para conversar com múltiplos provedores de IA por API, trabalhar em projetos locais, executar ferramentas controladas e oferecer uma experiência própria de agente.

A branch desta nova fase é:

feature/unified-ai-platform

Ela deve permanecer separada da main até validação completa.

1. VISÃO DO PRODUTO

O Auto CodeZ é um aplicativo desktop Electron para concentrar IAs externas em uma interface própria.

O usuário cadastra provedores usando suas próprias API keys. Cada chat utiliza uma única IA por vez. O usuário pode trocar a IA ativa no meio da conversa, mas não utiliza múltiplas IAs simultaneamente dentro do mesmo turno.

O aplicativo deve oferecer:

- login e perfil
- interface visual própria e moderna
- configurações globais
- configurações específicas por chat
- provedores de IA
- modelos
- capacidades multimodais
- chats
- histórico
- projetos
- workspace local
- edição de arquivos
- diffs
- criação, alteração, exclusão e renomeação de arquivos
- aprovação e rejeição de alterações
- níveis de acesso
- perfis de inteligência
- atividade de agente
- plugins e extensões
- armazenamento local
- futura sincronização, se fizer sentido

2. MUDANÇA FUNDAMENTAL DE ARQUITETURA

A arquitetura anterior dependia de:

Auto CodeZ
-> navegador
-> ChatGPT/Claude/Gemini web
-> Windows UI Automation
-> Chromium UIA
-> clipboard
-> SendKeys
-> leitura da interface

Essa arquitetura foi considerada limitada para o produto desejado.

A nova arquitetura é:

Auto CodeZ
-> AI Runtime
-> Provider Adapter
-> API
-> modelo

O Auto CodeZ não deve depender de automação visual de sites para o fluxo principal de IA.

A automação Chromium/UIA anterior fica arquivada como histórico técnico. Não deve receber novas funcionalidades no núcleo da plataforma, salvo decisão explícita futura.

3. STACK BASE

A base Electron + TypeScript + Vite deve ser mantida nesta fase.

Tecnologias atuais principais:

- Electron
- TypeScript
- Vite
- Electron Forge
- Monaco Editor
- Node.js no processo principal
- armazenamento local baseado em arquivos JSON inicialmente
- Electron safeStorage para API keys

React não é obrigatório neste estágio. A interface atual pode permanecer em TypeScript/DOM para evitar uma migração de dependências antes de a arquitetura estar estabilizada. A adoção de React ou outra camada de UI deve ser uma decisão posterior baseada em necessidade real.

4. PRINCÍPIO GLOBAL + INDIVIDUAL

O sistema não deve criar uma arquitetura isolada para cada IA.

O núcleo possui contratos globais.

Exemplos:

AIProvider
AIModel
AICapability
AIRequest
AIResponse
AIMessage
AIStreamEvent
AIToolCall
IntelligenceProfile
PermissionPolicy

Cada provider possui somente um adapter responsável por traduzir o contrato global para a API específica.

Arquitetura conceitual:

AI Runtime
|
+-- Provider Registry
|
+-- Capability Resolver
|
+-- Intelligence Runtime
|
+-- Tool Runtime
|
+-- Activity Runtime
|
+-- Permission Runtime
|
+-- Conversation Runtime
|
+-- Provider Adapters
     |
     +-- OpenAI
     +-- Google
     +-- Anthropic
     +-- outros no futuro

O restante do aplicativo não deve depender diretamente de detalhes da API de um provider.

5. PROVIDERS

Providers iniciais:

- OpenAI
- Google AI
- Anthropic

O sistema deve permitir novos providers sem reescrever o núcleo.

A arquitetura atual já possui:

src/ai/types.ts
src/ai/provider-registry.ts
src/ai/ai-runtime.ts
src/ai/providers/openai.ts
src/ai/providers/google.ts
src/ai/providers/anthropic.ts

O provider informa capacidades e modelos disponíveis.

6. API KEYS

O usuário cadastra a IA diretamente.

Interface conceitual:

Adicionar IA

IA
[ Google AI v ]

API Key
[ ******************************** ]

[ Testar e salvar ]

A detecção automática da IA por chave não é obrigatória. A seleção explícita do provider fica acima do campo da API key.

O Auto CodeZ valida a chave usando a API do provider e consulta os modelos disponíveis.

As API keys não devem aparecer no renderer nem ser armazenadas em texto puro quando o armazenamento seguro do sistema estiver disponível.

A implementação atual usa Electron safeStorage no processo principal e mantém somente metadados sem a chave em providers.json.

7. MODELOS E CAPACIDADES

A interface deve ser adaptativa.

Um modelo pode declarar capacidades como:

- text
- vision
- image
- video
- audio
- reasoning
- tools
- streaming

A UI deve mostrar recursos conforme as capacidades reais do modelo.

Não assumir que todos os providers ou modelos suportam as mesmas funções.

8. INTELIGÊNCIA

O usuário escolhe um perfil global do Auto CodeZ:

Baixo
Normal
Alto
Máximo

Isso não significa simplesmente quantidade de tokens.

O perfil representa um orçamento e nível de esforço desejado.

Baixo:

- respostas rápidas
- menor uso de recursos
- menor esforço de raciocínio

Normal:

- equilíbrio entre qualidade, velocidade e custo

Alto:

- mais esforço de raciocínio
- contexto maior quando disponível
- ferramentas adicionais quando apropriadas

Máximo:

- maior orçamento de raciocínio disponível no modelo
- maior esforço permitido pela capacidade real do provider

O Auto CodeZ traduz o perfil para a configuração equivalente de cada provider.

A UI nunca deve exigir que o usuário conheça a configuração específica de cada API para escolher o nível de inteligência.

9. CHAT

Cada chat possui uma única IA ativa por vez.

O usuário pode trocar a IA no meio do chat.

Exemplo:

Chat
-> Gemini
-> várias mensagens
-> usuário troca para Claude
-> conversa continua

O histórico pertence ao Auto CodeZ, não ao provider.

O runtime converte o histórico para o formato necessário do provider atual.

Não permitir uma seleção de múltiplos providers respondendo simultaneamente dentro do mesmo chat.

10. HISTÓRICO

Chats vazios não devem ser salvos como conversas úteis.

Um chat criado e abandonado antes de receber uma mensagem do usuário deve ser tratado como temporário e poderá ser descartado.

Depois da primeira mensagem, o chat passa a fazer parte do histórico.

Cada chat possui:

- id
- título
- projeto opcional
- provider atual
- modelo atual
- perfil de inteligência
- nível de acesso
- mensagens
- timestamps

Ao passar o cursor sobre o chat no histórico, aparece um ícone de engrenagem.

A engrenagem abre as configurações específicas daquele chat.

11. CONFIGURAÇÕES DO CHAT

Configurações esperadas:

- IA ativa
- modelo
- perfil de inteligência
- nível de acesso
- contexto do projeto
- futuras opções específicas de capacidade

A troca de IA no chat é permitida.

A troca de modelo também é permitida quando o modelo pertence ao provider configurado.

12. INTERFACE VISUAL

A identidade visual é própria do Auto CodeZ.

VS Code foi usado somente como referência estrutural, não como identidade a ser copiada.

A interface possui:

BARRA SUPERIOR

- horizontal
- permanente
- baixa altura
- marca do Auto CodeZ no extremo esquerdo
- ferramentas globais no lado direito
- configurações globais
- perfil

A ideia anterior de esconder ou minimizar a barra superior foi abandonada.

BARRA VERTICAL ESQUERDA

Possui ícones de navegação.

Inicialmente:

- Chats
- Projetos
- Plugins/Extensões
- Perfil no extremo inferior

Extensões futuras podem adicionar ícones próprios nessa barra.

PAINEL DE NAVEGAÇÃO

Ao clicar em Chats, o painel se expande e mostra o histórico.

Ao clicar em Projetos, mostra os projetos existentes.

Ao clicar em um projeto, mostra os chats daquele projeto.

O painel segue uma experiência semelhante à organização de ferramentas de desenvolvimento, mas possui identidade própria.

BARRA VERTICAL DIREITA

Por padrão não possui conteúdo.

Somente extensões podem adicionar conteúdo ou ícones ali.

CENTRO

O centro é o chat completo.

Mensagens do usuário usam balões azuis.

Mensagens da IA usam o estilo padrão do aplicativo.

13. COMPOSER

Na parte inferior do chat existe o campo:

Digite uma mensagem...

Ao lado do campo existe o botão para anexar arquivos, imagens e outros conteúdos.

O nível de inteligência fica separado do botão de anexos e do campo.

A composição conceitual é:

[ + / anexar ] [ Digite uma mensagem... ] [ Inteligência v ] [ enviar ]

A IA ativa não precisa aparecer dentro do composer. Ela deve ficar identificada no cabeçalho/configurações do chat.

14. ATIVIDADE DO AGENTE

O Auto CodeZ deve mostrar atividade observável da IA durante trabalhos complexos.

Não exibir raciocínio interno privado do modelo.

Exibir mensagens operacionais e explicativas semelhantes a uma experiência de agente de desenvolvimento.

Exemplos:

Encontrei uma falha crucial no arquivo. Vou verificar como o fluxo atual funciona.

Vou atualizar a validação da sessão.

Executei os testes e todos passaram. Agora vou executar a build.

A atividade não deve ser limitada a uma simples lista fixa de etapas.

Ela deve acompanhar ações reais do runtime e das ferramentas.

15. ACTIVITY RUNTIME

A camada global src/core/activity-runtime.ts registra eventos observáveis.

Tipos previstos:

- thought
- action
- tool
- test
- build
- complete
- error

Status:

- pending
- running
- success
- failed

A atividade deve servir para a UI acompanhar trabalho de agente sem depender do texto cru de uma resposta final.

16. PROJETOS

O usuário cria um projeto apontando para uma pasta local.

Um projeto possui:

- id
- nome
- caminho local
- timestamps

O projeto pode conter vários chats.

Um chat pode existir fora de projeto.

A estrutura deve suportar futuramente:

- contexto persistente
- arquivos abertos
- Git
- instruções do projeto
- ferramentas
- permissões
- agentes

17. WORKSPACE

O Auto CodeZ deve tratar o projeto como workspace quando a IA receber autorização para trabalhar em arquivos.

Ferramentas conceituais:

read_file()
write_file()
create_file()
delete_file()
rename_file()
search_files()
run_command()

A IA não deve receber acesso arbitrário ao sistema operacional simplesmente por estar em modo agente.

O runtime fornece ferramentas controladas.

18. PERMISSÕES

Níveis iniciais:

Somente leitura

A IA pode analisar o workspace, mas não alterar arquivos.

Acesso seguro

A IA pode executar operações consideradas seguras dentro do workspace. Operações destrutivas ou sensíveis exigem proteção adicional.

Acesso solicitado

Operações de alteração relevantes podem ser apresentadas ao usuário para aprovação.

Acesso irrestrito

O usuário permite que a IA execute operações sem confirmação individual, dentro das regras do runtime.

Mesmo no modo irrestrito, a arquitetura deve possuir proteções estruturais contra operações destrutivas fora do workspace quando isso for tecnicamente aplicável.

O objetivo é evitar acidentes como excluir diretórios críticos do sistema.

19. PROPOSTAS E ALTERAÇÕES

Quando a IA alterar um projeto, o Auto CodeZ deve mostrar:

- arquivos criados
- arquivos modificados
- arquivos excluídos
- arquivos renomeados
- diff
- operações executadas
- testes executados
- build executada

A interface deve permitir aceitar ou recusar alterações.

O sistema deve separar:

proposta
-> revisão
-> aprovação
-> aplicação

Nenhuma alteração deve ser aplicada silenciosamente quando o nível de acesso exigir aprovação.

20. DIFERENÇAS

O Monaco Editor continua sendo a base do editor.

O sistema deve conseguir mostrar diffs de arquivo e conjuntos de alterações.

Estados possíveis de uma alteração:

- pending
- accepted
- rejected
- applied
- failed

21. PLUGINS

Plugins são parte central da arquitetura futura.

Um plugin pode contribuir com:

- ícone na barra esquerda
- painel na barra direita
- comando
- provider
- ferramenta
- tema
- integração

A implementação inicial possui src/plugins/plugin-registry.ts.

O sistema de plugins deve crescer sem exigir alterações manuais no núcleo para cada extensão.

22. LOGIN E PERFIL

Login faz parte da visão do produto, mas a primeira etapa do runtime é local-first.

O perfil local existe como espaço inicial de UI.

Autenticação real, conta online, sincronização e licenciamento devem ser adicionados quando houver uma arquitetura de backend definida.

Não criar um falso sistema de login que pareça conectado a um servidor inexistente.

23. ARMAZENAMENTO

A primeira implementação usa arquivos locais no diretório de dados do Electron.

Arquivos conceituais:

providers.json
provider-keys.dat
projects.json
chats.json

API keys devem ficar criptografadas por safeStorage.

No futuro, o armazenamento de chats/projetos poderá migrar para SQLite quando a quantidade de dados e consultas justificar.

24. AI RUNTIME

O runtime central atual é:

src/ai/ai-runtime.ts

Ele recebe mensagens, modelo, provider e perfil de inteligência e encaminha a solicitação ao adapter correto.

A aplicação não deve espalhar chamadas HTTP específicas de provider pela UI.

25. PROVIDER REGISTRY

src/ai/provider-registry.ts é responsável por registrar adapters e resolver providers.

A UI e os runtimes devem depender dos contratos globais, não de classes concretas sempre que possível.

26. ADAPTERS

Adapters atuais:

src/ai/providers/openai.ts
src/ai/providers/google.ts
src/ai/providers/anthropic.ts

Eles traduzem contratos globais para APIs específicas.

A implementação inicial usa chamadas HTTP no processo principal.

Streaming, tool calling completo, multimodalidade e loops de agente serão aprofundados nas etapas seguintes.

27. SEGURANÇA

API keys nunca devem ser colocadas no renderer.

Chamadas de provider devem ocorrer no processo principal.

O preload deve expor somente funções IPC necessárias.

O renderer deve permanecer sem acesso direto a Node.js.

contextIsolation deve permanecer habilitado.

nodeIntegration deve permanecer desabilitado.

Ferramentas de agente devem passar por Permission Runtime.

31. PRINCÍPIO DE EVOLUÇÃO

Não criar abstrações específicas de provider no núcleo quando uma capacidade global resolver o problema.

Não criar uma API universal falsa que esconda diferenças importantes dos modelos.

O adapter deve preservar diferenças reais quando necessário, mas apresentar um contrato comum para o restante do aplicativo.

32. PRINCÍPIO DE UX

O usuário deve pensar em:

IA
Modelo
Inteligência
Acesso
Projeto

O usuário não deve precisar pensar em:

endpoints
payloads
headers
formato interno de tool calling
mapeamento de tokens
particularidades de cada SDK

O Auto CodeZ deve traduzir a complexidade para uma experiência consistente.

33. PRINCÍPIO DE TROCA DE IA

Trocar a IA ativa no meio do chat é permitido.

O histórico continua pertencendo ao chat.

O provider atual muda somente para as próximas solicitações.

O runtime deve converter mensagens e capacidades conforme o novo provider.

34. PRINCÍPIO DE FALHA SEGURA

Se uma operação de agente não possuir permissão suficiente, não executar.

Se uma ferramenta estiver indisponível, informar o usuário.

Se uma resposta do provider falhar, não corromper o histórico.

Se uma alteração falhar parcialmente, registrar o estado e não esconder a falha.

35. ARQUIVAMENTO DA AUTOMAÇÃO DE NAVEGADOR

O trabalho anterior de automação Chromium/UIA permanece como histórico técnico.

Arquivos históricos incluem:

src/automation/browser.ts
src/automation/windows-ui.ts
src/automation/chromium-ai-input.ts
src/automation/ai-response-reader.ts
src/automation/providers/chatgpt.ts
src/automation/providers/claude.ts
src/automation/providers/gemini.ts

Esses arquivos não representam mais o núcleo do produto.

O incidente final registrado na arquitetura anterior foi:

- clipboard finalmente recebeu o prompt corretamente
- o prompt não foi colado no editor web
- isso apontou para problemas de foco efetivo/SendKeys e para a fragilidade da automação visual

Esse incidente contribuiu para a decisão de abandonar a automação de navegador como núcleo.

A branch feature/unified-ai-platform contém a primeira fundação da nova arquitetura.

Ela já possui:

- registry de providers
- AI Runtime
- adapters OpenAI, Google e Anthropic
- armazenamento seguro de API keys
- gerenciamento de projetos
- gerenciamento de chats

- novo renderer
- novo design visual

Esta etapa é fundacional. Não considerar todos os recursos de agente como completos ainda.

37. REGRA PARA FUTURAS ALTERAÇÕES

Antes de alterar o núcleo:

1. Ler este arquivo inteiro.
2. Verificar a branch atual.
3. Confirmar que a mudança pertence à arquitetura global.
4. Evitar reintroduzir dependência de navegador para chamadas de IA.
5. Não colocar API keys no renderer.
6. Preservar a separação entre provider adapter e runtime global.
7. Testar TypeScript e empacotamento.
8. Não publicar diretamente na main durante desenvolvimento.

A main somente recebe alterações depois de revisão e aprovação explícita.

38. OBJETIVO FINAL

O Auto CodeZ deve ser uma plataforma própria de IA para desenvolvimento e uso geral.

O usuário entra no aplicativo, configura suas IAs, cria um chat ou projeto e trabalha dentro da mesma interface.

A plataforma deve permitir conversa, criação de conteúdo, multimodalidade, projetos, edição de arquivos, agentes, ferramentas, permissões e extensões.

A arquitetura deve ser global no núcleo e individual somente nos adapters e capacidades específicas de cada provider.
