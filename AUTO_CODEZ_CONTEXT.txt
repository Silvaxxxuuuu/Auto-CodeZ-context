2. O QUE É O AUTO CODEZ
============================================================

Auto CodeZ é um aplicativo desktop local-first para desenvolvimento e automação assistidos por IA.

Stack principal:
- Electron;
- Vite;
- TypeScript;
- Node.js;
- Electron Forge;
- Monaco Editor;
- xterm.js / node-pty onde aplicável;
- DOM/TypeScript na UI atual;
- armazenamento local + safeStorage/protected stores para secrets.

Objetivo de produto:
- chat multiprovider;
- projetos/workspaces locais;
- agente capaz de editar, criar, remover e organizar arquivos;
- execução controlada de comandos;
- processos persistentes;
- instances/previews;
- Git;
- Web/research;
- plugins;
- MCP como cliente e servidor;
- attachments/vision;
- memória e personalização;
- artifacts;
- geração de imagens;
- multi-agent/orchestration;
- automação especializada futura para Roblox, Blender e animação.

Princípio:
o contexto, estado, evidência, journal, memória operacional e execução pertencem ao Auto CodeZ, não ao provider.

Fluxo conceitual:
UI
-> ChatRuntime / ContextCompiler
-> Provider Adapter
-> AgentRuntime
-> Capability/Policy/ToolRuntime
-> workspace/process/instance/Git/Web/plugin/MCP
-> evidence/journal/activity/ledger
-> resposta final factual.

O provider externo nunca recebe acesso bruto ao sistema operacional.

16. SHADOW WORKSPACE — RETIREMENT
============================================================

Shadow Workspace NÃO é mais caminho normal de runs V2.

Estado:
compatibility-only.

Regras:
- runs V2 novas não criam shadow;
- beginLegacy() é criação explícita de legado;
- código de produção não deve chamar beginLegacy();
- guard arquitetural falha CI se caller novo surgir;
- workspace() exige shadow legado preexistente;
- sem shadow, fail closed;
- command sandbox V2 não cria shadow;
- Git não cria shadow;
- lifecycle só commit/discard de legado existente;
- shadow-git-read existe apenas para visão read-only de overlay legado.

Persistência:
- bootstrap mantém somente snapshots ativos ligados a runs pendentes/recoverable;
- órfãos são descartados;
- restore emite estado reconciliado;
- subscriber persiste lista reconciliada;
- snapshot órfão some do storage;
- snapshot recuperável sobrevive e some após discard.

Razão restante para manter Shadow:
compatibilidade com snapshots persistidos antigos de runs pendentes/recoverable.

Não remover fisicamente até concluir acceptance e confirmar que migration/legacy retention pode acabar.

18. PROGRESS WATCHDOG / LONG-RUN
============================================================

Não existe teto artificial pequeno de tool rounds.

Watchdog:
- permite muitos rounds se houver progresso novo;
- detecta A/A;
- detecta A/B/A/B;
- usa evidence/progress keys;
- força replan antes de parar;
- erro novo pode ser progresso diagnóstico;
- erro repetido não;
- approval/external wait não consome stagnation budget;
- estado pode ser snapshot/restored;
- raw input não precisa ser persistido.

Objetivo:
tarefas grandes podem continuar por muito tempo sem serem mortas por contador fixo.

============================================================
19. RECOVERY / CANCELLATION / RETRY
============================================================

Recovery:
- provider-failed run pode ser retomado sem reexecutar tool aplicada;
- write-ahead journal impede mutation duplicada;
- pending approvals são recuperáveis;
- stale approvals não ressuscitam run morto.

Cancellation:
- estado canônico cancelled;
- diferente de failed/interrupted;
- ledger/report/visibility reconhecem cancelled;
- explicit Stop preserva histórico;
- cancelChat limpa approvals internamente;
- recovery cancelada preserva snapshot terminal;
- delete/cleanup usa interrupted quando semanticamente correto.

Retry:
- retry de resposta cria nova variante/run;
- não repete side effects cegamente;
- workspace atual + journal precisam ser considerados;
- resposta antiga não é apagada.
