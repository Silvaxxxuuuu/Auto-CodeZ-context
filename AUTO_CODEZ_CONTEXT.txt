============================================================
1. PRODUTO
============================================================

Auto CodeZ é um aplicativo desktop real em Electron + Vite + TypeScript. É uma plataforma local-first de desenvolvimento assistido por IA, projetada para trabalhar com muitos provedores e modelos, com interface própria, agente, execução controlada de ferramentas, projetos locais, chats, configurações, plugins futuros e conta/sincronização.

O objetivo não é construir um aplicativo dependente somente de Anthropic, Google AI e OpenAI/ChatGPT. Esses são apenas os providers iniciais. A visão de longo prazo é suportar o maior número possível de provedores de IA que ofereçam APIs utilizáveis pelo usuário, respeitando capacidades, termos, autenticação, limites e compatibilidade técnica de cada serviço.

Arquitetura antiga baseada em automação de navegador/UI Automation para ChatGPT, Claude e Gemini não é mais o núcleo.

Fluxo principal:
Auto CodeZ -> AI Runtime -> Provider Adapter -> API -> modelo.

Tratar como software de produção: mudanças incrementais, código limpo, validação real, sem refatorações amplas sem necessidade.

Visão de produto:
- chatbot conversacional;
- histórico e memória de conversas;
- contexto de workspace/projeto;
- edição direta de arquivos no PC do usuário;
- criação, alteração, exclusão e organização de arquivos;
- execução de comandos e ferramentas sob controle do Auto CodeZ;
- automação ampla por agentes;
- testes, builds e outras tarefas de desenvolvimento;
- geração de imagens quando o provider/modelo permitir;
- geração de áudio quando o provider/modelo permitir;
- geração de vídeo quando o provider/modelo permitir;
- visão/multimodalidade quando suportada;
- reasoning quando suportado;
- tool calling e agentes;
- futura arquitetura de plugins, integrações e automações.

O produto deve tratar capacidades como propriedades reais de cada modelo/provider. Não prometer uma modalidade que o provider ou modelo não suporta.

A IA deve poder trabalhar diretamente no ambiente local do usuário, mas nunca deve receber acesso arbitrário ao sistema operacional apenas por estar em modo agente. Execução, permissões, sandbox, aprovação e observabilidade são partes centrais da arquitetura.

5. ABSTRAÇÃO MULTIPROVIDER E VERCEL AI SDK
============================================================

Foi identificada a possibilidade de utilizar o Vercel AI SDK como camada de abstração TypeScript para consumo uniforme de múltiplos modelos/providers e modalidades, especialmente text generation, streaming, tool calling, structured output e recursos multimodais quando suportados.

A ideia é arquiteturalmente relevante para o Auto CodeZ porque o produto pretende suportar muitos providers e modalidades. Entretanto, o AI SDK não deve assumir o controle das abstrações próprias do Auto CodeZ.

Princípio desejado:
Auto CodeZ AI Runtime -> camada de adapters/abstração -> provider/modelo

O Vercel AI SDK pode ocupar a camada de infraestrutura/abstração se, após um spike técnico, demonstrar que reduz complexidade sem prejudicar:
- BYOK / API keys próprias do usuário;
- seleção por apiKeyId;
- safeStorage;
- ProviderManager;
- ModelResolver;
- ChatRuntime;
- capabilities reais;
- permissões;
- Execution Manager;
- sandbox;
- Electron IPC;
- execução local;
- tratamento de erros e indisponibilidade;
- histórico/memória do Auto CodeZ;
- suporte a providers que não sejam cobertos nativamente pelo SDK.

Não adotar o AI SDK apenas por conveniência. Antes da adoção, comparar o custo de manter adapters próprios com o benefício real da abstração. Se a integração for extremamente vantajosa, ele pode se tornar a camada padrão de consumo de modelos do Auto CodeZ, sem substituir o domínio e as regras do próprio Auto CodeZ.

Não tornar o AI Gateway de terceiros uma dependência obrigatória do produto. A visão principal continua sendo local-first + BYOK: sempre que possível, Auto CodeZ -> provider diretamente usando a credencial do usuário.

Futuro desejado:
- provider adapters finos;
- registry extensível;
- discovery de modelos/capabilities;
- normalização de requests/responses/stream events;
- suporte a modalidades heterogêneas;
- fallback/retry controlados sem trocar silenciosamente a identidade da credencial;
- possibilidade de providers adicionais sem alterações profundas no core.

6. API KEYS, CREDENCIAIS E ERROS
============================================================

Fluxo:
provider -> nome -> API Key -> modelo/base URL opcional -> validação -> model discovery -> salvar.

API Keys são secrets. Localmente usar safeStorage. Nunca salvar plaintext em providers.json.

ApiKeySummary inclui conceitualmente:
- id;
- name;
- providerId;
- providerName;
- maskedKey;
- selectedModel;
- active.

Uma credencial salva possui identidade própria. O nome informado pelo usuário deve ser preservado exatamente.

Exemplos de nomes:
- Minha Gemini principal
- Google trabalho
- Claude pessoal
- OpenAI produção
- Gemini testes

Se o usuário tiver várias chaves do mesmo provider, o chat deve selecionar a credencial específica, e não somente o provider.

Persistência de chat usa apiKeyId.

Regras atuais:
- chat persiste o apiKeyId exato;
- runtime resolve exatamente essa credencial;
- provider é derivado/verificado a partir da credencial selecionada;
- chat pode trocar de credencial/provider/modelo;
- remover uma credencial não deve silenciosamente trocar chats existentes para outra credencial;
- se a credencial exata de um chat for removida, a UI de configurações do chat não deve inventar um estado “credencial ausente” nem selecionar automaticamente outra;
- a lista deve mostrar somente credenciais atualmente existentes;
- se o usuário fechar sem salvar, o apiKeyId antigo pode permanecer persistido e o runtime deve continuar recusando a credencial inexistente;
- selecionar e salvar uma nova credencial substitui explicitamente o apiKeyId;
- uma nova chave com o mesmo nome nunca deve ser confundida com a antiga, pois IDs são distintos.

Arquivos envolvidos:
- src/ai/chat-manager.ts
- src/ai/types.ts
- src/ai/provider-manager.ts
- src/main.ts
- src/preload.ts
- src/chat-api-key-settings-ui.ts
- tests/chat-saved-api-key-selection.test.ts

Testes atuais cobrem:
1. persistência da credencial exata;
2. preservação da credencial ao alterar somente modelo/inteligência;
3. limpeza de credencial obsoleta quando provider muda sem nova credencial;
4. resolução da credencial exata em vez da credencial ativa do provider.

Erros devem distinguir:
authentication, billing, quota, rate limit, network, server, invalid request e unknown.

Estado observado em 01/09/2026:
- Google AI respondeu corretamente a um primeiro “olá”.
- Depois, criação de pasta retornou falta de créditos/cota.
- OpenAI e Anthropic também estavam sem créditos no momento.
- Isso prova que o fluxo alcança os providers.
- Prioridade é classificação e apresentação correta de billing/quota, não erro genérico.

8. SANDBOX E SEGURANÇA DE EXECUÇÃO — FUTURO PRIORITÁRIO
============================================================

O sandbox é uma das próximas grandes áreas arquiteturais porque o Auto CodeZ pretende permitir que a IA edite o PC e execute ferramentas.

Objetivo:
IA -> tool call -> policy/permission -> sandbox ou executor controlado -> filesystem/processo -> resultado observável.

Não permitir como arquitetura final:
IA -> child_process arbitrário -> sistema operacional inteiro.

A solução futura deve considerar isolamento de processos, workspace boundaries, allowlists/denylists, confirmação de operações perigosas, cancelamento, timeouts, limites de recursos, captura de stdout/stderr, auditoria e recuperação de falhas.

A arquitetura deve permitir automação forte sem transformar o Auto CodeZ em um mecanismo de execução cega de comandos.

18. LOCAL-FIRST / OFFLINE
============================================================

Decisão arquitetural permanente:
AUTO CODEZ = LOCAL-FIRST + CLOUD SYNC + OFFLINE QUEUE + BYOK.

Se internet cair:
- sessão não é perdida;
- chats/histórico/contexto local continuam disponíveis;
- projetos locais continuam disponíveis;
- configurações continuam disponíveis;
- alterações continuam salvas localmente;
- operações dependentes da cloud ficam pendentes;
- UI permanece utilizável.

Quando internet voltar:
- fila é processada;
- servidor confirma;
- estado vira sincronizado;
- conflitos são apresentados quando necessário.

Regra: nunca apagar alteração local porque sync falhou.

Fluxo:
alteração local -> salvar localmente -> fila -> tentar sync -> confirmação -> sincronizado.
Falha -> salvo localmente + pending.

BYOK:
Sempre que a integração permitir, o usuário fornece e controla sua própria API key. O Auto CodeZ não deve obrigar o usuário a usar uma conta/proxy proprietário para conversar com um modelo externo.

23.1. MONACO DIFF REVIEW E EDIÇÃO CONTROLADA
------------------------------------------------------------

Monaco Editor já faz parte das dependências do Auto CodeZ e foi integrado como base para revisão visual de alterações.

Estado técnico validado antes desta atualização:
- commit 787795ddabd63f4b926d14a71861b2ed0e77898b;
- CI 33894085579 completamente verde;
- Monaco Diff Review empacota no Electron Forge e passa startup smoke test.

Arquitetura desejada:
approval.diffPlan -> Revisar alterações -> Monaco Diff Editor -> Aprovar/Recusar -> ApprovalRuntime/AgentRuntime -> ToolRuntime aplica a mudança.

Monaco é visualizador/revisor, não executor paralelo. Não criar segundo runId, segundo approval flow ou aplicação direta independente do ToolRuntime.

Problema descoberto no teste manual:
- a IA ainda escolhe run_command/PowerShell para escrever código em alguns casos;
- quando isso acontece não existe DiffPlan de arquivo e o botão Revisar alterações não aparece;
- isso contorna a revisão de arquivo apesar de a operação ainda pedir aprovação de comando.

Decisão:
- para criar/editar/excluir/renomear arquivos, a IA deve preferir create_file/write_file/delete_file/rename_file;
- run_command deve ser priorizado para npm, testes, builds, scripts, CLIs, ferramentas externas e comandos realmente apropriados ao shell;
- não usar shell como editor de arquivos quando as file tools puderem representar a operação;
- mudanças de arquivo devem passar pelo DiffRuntime e, quando aplicável, Monaco Diff Review.

Futuro desejado:
- revisão multi-arquivo;
- Aprovar tudo / Recusar tudo;
- revisão individual por arquivo;
- before/after;
- contagem de linhas;
- linguagem/syntax highlighting;
- precondition contra arquivo alterado desde o preview;
- aplicação somente depois de aprovação.

23.14. ORCHESTRATOR / MULTI-AGENT
------------------------------------------------------------

Funcionalidade central futura aprovada: duas ou mais IAs podem colaborar para concluir um projeto inteiro a partir de um único prompt.

Primeira versão deve priorizar duas funções:

Supervisor:
- interpreta objetivo;
- planeja;
- define arquitetura;
- pesquisa limitações quando permitido;
- cria critérios de aceitação;
- revisa implementação;
- detecta problemas;
- sugere abordagem melhor;
- controla qualidade;
- decide quando a tarefa realmente terminou.

Executor:
- lê workspace;
- implementa;
- usa file tools;
- executa comandos;
- cria testes;
- builda;
- corrige falhas;
- devolve resultados estruturados.

Fluxo desejado:
prompt -> Supervisor -> TaskPlan estruturado -> Auto CodeZ -> Executor -> ExecutionReport -> Supervisor -> revisão -> novas tarefas/correções -> Executor -> validação final -> entrega.

Não permitir que duas IAs simplesmente conversem indefinidamente em texto livre, pois isso desperdiça tokens e perde controle.

Usar estruturas do domínio do Auto CodeZ, por exemplo:
TaskPlan:
- objetivo;
- etapas;
- critérios de aceitação;
- arquivos relevantes;
- testes necessários.

ExecutionReport:
- etapas concluídas;
- arquivos alterados;
- testes;
- erros;
- observações;
- próximos bloqueios.

O Supervisor e o Executor podem usar providers/modelos diferentes ou o mesmo provider/modelo.

Exemplos:
- Supervisor Claude / Executor Gemini;
- Supervisor GPT / Executor DeepSeek;
- mesma IA nos dois papéis, se necessário.

A arquitetura deve nascer extensível para papéis adicionais sem exigir que todos sejam ativados:
- Reviewer;
- Researcher;
- Tester;
- Security Agent;
- Documentation Agent;
- Frontend Agent;
- Backend Agent.

O Supervisor pode convocar agentes especializados somente quando necessário.

23.16. AUTO CHANGE / CONTINUIDADE ENTRE MODELOS

O contexto pertence ao Auto CodeZ, não ao provider.

- objetivo;

- approvals;

Possíveis gatilhos:
- billing/sem créditos;
- quota atingida;

- priorizar qualidade;
- priorizar velocidade;
- permitir OpenRouter;

Supervisor: Claude -> GPT -> Gemini.

24.12. FRONTEIRA REAL QUE AINDA NÃO ESTÁ RESOLVIDA
------------------------------------------------------------

O command sandbox atual é substancialmente mais hermético, mas não é um sandbox de sistema operacional completo.

Já endurecido:
- workspace temporário;
- Shadow Workspace;
- paths sensíveis excluídos da materialização;
- symlink/junction validado;
- ambiente de processo sanitizado;
- home/config/cache/temp isolados;
- SYSTEM_PROJECT_ID executado contra cópia temporária;
- Git sem configuração de sistema e sem prompts interativos;
- principais variáveis de startup injection removidas;
- aprovação explícita continua obrigatória quando ExecutionPathScope não consegue provar confinamento do shell.

Ainda não provado/confinado pelo sistema operacional:
- acesso direto a paths absolutos fora do sandbox por um comando aprovado;
- acesso de rede do processo filho;
- mecanismos de credencial mantidos pelo próprio sistema operacional ou por ferramentas externas fora das variáveis já sanitizadas;
- acesso a recursos do usuário concedidos pelo token normal do processo;
- isolamento de processo contra outras superfícies do Windows.

Não tentar resolver isso com regex de comandos, blacklist crescente de strings ou afirmação falsa de que uma allowlist de paths confina um shell geral.

Próximo passo correto:
- fazer um spike técnico específico de isolamento real de processo no Windows;
- avaliar mecanismos compatíveis com Electron/Node e distribuição desktop;
- separar claramente Job Object/limites de processo de isolamento de filesystem/token/rede;
- definir comportamento quando isolamento forte não estiver disponível;
- preservar approval explícita como fallback de segurança;
- somente depois decidir qual implementação de process sandbox entra na Fase 3.

Até essa decisão, run_command continua sendo uma ferramenta aprovada e controlada, mas não deve ser descrita como execução totalmente confinada pelo SO.

Anexar uma pasta pelo "+" NÃO transforma a pasta em workspace gravável.

-> construção de contexto relevante
-> análise pelo modelo

Isso cria duas camadas diferentes:
1. nível geral de permissão/autonomia do Roblox Studio Manager;
2. fronteira independente de escrita de pastas anexadas.

24.27. AUTO CODEZ MCP GATEWAY + MCP MODE — DIREÇÃO CENTRAL
------------------------------------------------------------

DECISÃO DE ARQUITETURA

O Roblox Studio MCP continua necessário e deve ser finalizado. Existem duas direções MCP independentes e complementares:

ENTRADA:
IA/cliente MCP externo -> Auto CodeZ MCP Gateway -> AgentRuntime -> políticas/aprovações -> PluginToolCatalog -> plugins.

SAÍDA:
Auto CodeZ -> Roblox Studio Manager -> MCP oficial do Roblox Studio -> Roblox Studio.

Portanto, conectar ChatGPT/Claude/outros ao Auto CodeZ NÃO substitui a ponte oficial com o Roblox Studio. O Gateway torna o Auto CodeZ servidor MCP; o Roblox Studio Manager mantém o Auto CodeZ como cliente MCP do Studio. O objetivo estrutural é Auto CodeZ consumir e oferecer MCP.

Motivação:
- evitar que o produto dependa de um único fornecedor de IA;
- permitir que usuários usem clientes/modelos aos quais já tenham acesso quando a integração oficial suportar as ações necessárias;
- API própria e modelos locais permanecem opções, não requisitos arquiteturais;
- não prometer uso ilimitado, nem assumir que assinatura de chat equivale a API;
- não automatizar/scrapear interfaces web para transformar assinaturas em APIs.

O Gateway externo NÃO deve contornar AgentRuntime, Allowed Paths, approval policy, attachment write boundary ou PluginToolCatalog. Toda mutação continua atravessando as fronteiras autoritativas existentes. Não expor shell/FS bruto como atalho.

MCP MODE — SUPERFÍCIE OPERACIONAL

Nova decisão de produto: criar um modo chamado conceitualmente MCP Mode. Ele NÃO é um segundo chat conversacional e NÃO possui composer/campo de digitação.

Quando uma IA externa opera o Auto CodeZ via MCP, MCP Mode funciona como ledger/timeline ao vivo e auditável da sessão. A UI deve registrar ações reais do runtime em linguagem humana, por exemplo:
- Verificou a árvore da experiência
- Leu src/shared/...
- Alterou src/shared/... (Roblox Studio) +370 -14
- Executou build: ...
- Iniciou Play
- Simulou W/A/S/D
- Capturou viewport
- Leu console
- Pesquisou ...
- Consultou fonte ...
- Gerou imagem ...
- Chamou plugin/tool ...
- Aguardando aprovação
- Operação recusada/falhou/concluiu

Não gerar eventos falsos a partir de texto do modelo. A timeline deve nascer de eventos estruturados e autoritativos do AgentRuntime, PluginToolCatalog, jobs, ferramentas, providers e plugins.

OBJETIVO DO MCP MODE

1. Dar observabilidade quase total ao usuário enquanto uma IA externa trabalha.
2. Permitir auditoria posterior: o usuário deve saber o que foi lido, alterado, executado e testado.
3. Servir como memória operacional recuperável quando o cliente de IA perder contexto.
4. Permitir que uma nova sessão/IA reconstrua o estado do trabalho sem depender de todo o histórico textual original.
5. Tornar execução longa compreensível sem transformar cada tool call em ruído técnico.

IMPORTANTE: “contexto ilimitado” deve ser entendido como histórico persistente/recuperável, NÃO como uma janela de contexto infinita enviada ao modelo. O sistema deve compactar/indexar/retrieval sob demanda.

MODELO DE EVENTO RECOMENDADO

Cada evento deve possuir, quando aplicável:
- eventId
- sessionId
- runId
- parent/causation id
- timestamp
- actor/provider/client
- plugin/tool
- project/workspace/place
- categoria (inspect/read/write/execute/test/search/source/media/approval/error/system)
- estado (started/progress/completed/failed/cancelled/denied)
- resumo humano
- dados estruturados mínimos
- duração
- arquivos/Instances afetados
- diff stats (+/-) quando houver
- artifact refs (screenshot, imagem, log, relatório)
- source refs quando pesquisa/fonte existir
- error/diagnostic sanitizado
- approval id quando existir.

Não persistir secrets, tokens, credenciais, conteúdo sensível desnecessário ou stdout ilimitado. Payloads grandes devem virar artifacts com limites/retenção, e o ledger guarda referência/resumo.

CAMADAS DE VISUALIZAÇÃO

A timeline deve ter disclosure progressivo:
- padrão: ações humanas importantes;
- expandido: arquivo/Instance, duração, diff stats, resultado;
- técnico/diagnóstico: tool id, plugin id, request ids, payload sanitizado, protocolo.

Filtros úteis:
- Tudo
- Alterações
- Execuções/Testes
- Roblox
- Arquivos
- Pesquisas/Fontes
- Mídia
- Aprovações
- Erros

Agrupar eventos repetitivos. Ex.: dezenas de reads podem aparecer como “Inspecionou 18 arquivos”, expansível.

IDEIAS ADICIONAIS FECHADAS COMO DIREÇÃO

A) SESSION CAPSULE / HANDOFF
Ao encerrar ou pausar uma sessão MCP, gerar uma cápsula estruturada:
- objetivo atual;
- alterações realizadas;
- arquivos/Instances tocados;
- testes executados e resultados;
- erros ainda abertos;
- decisões/aprovações;
- próximos passos;
- artifacts/fontes relevantes.
Uma nova IA pode solicitar essa cápsula para retomar trabalho com baixo custo de contexto.

B) CHECKPOINTS
Permitir checkpoints nomeados/automáticos antes de operações grandes e playtests. Checkpoint não significa necessariamente git commit. Deve registrar estado suficiente para comparação/rollback quando a integração subjacente suportar.

C) DIFF FIRST
Toda mutação de arquivo/script deve produzir diff stats e, quando possível, diff visual expansível. Para Roblox Instances/propriedades, produzir equivalente estrutural before/after.

D) LIVE RUN HEADER
MCP Mode deve mostrar no topo: cliente/IA conectada, projeto/Place, run atual, duração, estado, nível de autonomia e Stop. Stop deve cancelar o job real.

E) APPROVALS INLINE
Aprovações aparecem na timeline e usam a mesma política autoritativa. Nunca conceder permissão apenas porque o cliente MCP pediu.

F) ARTIFACT STRIP
Screenshots de playtest, imagens geradas, relatórios e logs importantes devem ficar ligados ao evento e também acessíveis numa visão de artifacts da sessão.

G) SEARCH/SOURCE PROVENANCE
Quando uma capability real de pesquisa for usada, registrar consulta, domínio/fonte, timestamp e relação com a ação subsequente. Não fingir provenance se o provider não fornecer dados estruturados.

H) CONTEXT EXPORT
Expor ao cliente MCP ferramentas de recuperação controlada, por exemplo conceitualmente:
- session_summary
- session_recent_events
- session_changes
- session_errors
- session_artifacts
- session_sources
Isso permite recuperar contexto sob demanda sem reenviar o ledger inteiro.

I) REPLAY NÃO É REEXECUÇÃO
A timeline pode reconstruir o que ocorreu, mas não deve automaticamente repetir ações mutáveis. Qualquer “reexecutar” é uma nova operação sujeita às políticas atuais.

J) RETENÇÃO E PERFORMANCE
Ledger persistente deve ser append-oriented, paginado e indexado por session/run/category/resource. Não manter tudo no DOM nem carregar logs gigantes na memória. Definir retenção/limites configuráveis.

K) MULTI-CLIENT FUTURO
O modelo deve suportar identificar cliente/provider por sessão para que ChatGPT, Claude ou outro cliente MCP possam operar sem misturar autoria/estado.

MCP MODE vs CHAT NORMAL

Chat normal:
- usuário conversa diretamente no Auto CodeZ;
- possui composer;
- provider selecionado pelo Auto CodeZ;
- timeline de ferramentas pode aparecer como suporte à conversa.

MCP Mode:
- nenhuma caixa de texto;
- cliente externo é o cérebro/conversação;
- Auto CodeZ é executor/orquestrador e observador;
- tela principal é timeline/ledger + approvals + artifacts + status.

POP-UP FLUTUANTE

O pop-up já especificado continua sendo a superfície de comando para Chat normal. Quando uma sessão MCP externa estiver ativa, ele pode opcionalmente entrar em estado observador compacto, mostrando atividade atual/approval/Stop, sem inventar um composer MCP.

1. Finalizar/harden MCP stdio cliente e Roblox Studio Manager.
2. Fechar camada Roblox estável e playtest visual.
3. Criar event ledger interno independente de UI, aproveitando eventos reais já existentes.
4. Criar MCP Mode como projeção desse ledger.
5. Implementar Auto CodeZ MCP Gateway como servidor, sempre atrás do AgentRuntime/policies.
6. Implementar Session Capsule/retrieval.
7. Conectar/testar clientes MCP suportados (ChatGPT/Claude/outros) conforme capacidades oficiais disponíveis.
8. Refinar multi-client, artifacts, provenance, checkpoints e handoff.

FASE C — RELAY PROTOCOL V1
============================================================

Executar depois de Account + Device Registry.

Objetivo:
permitir que o Auto CodeZ Desktop mantenha uma conexão outbound segura com a infraestrutura Auto CodeZ.

Topologia:

Auto CodeZ Desktop
→ HTTPS/WSS outbound
→ Auto CodeZ Relay.

Nenhuma porta inbound é necessária no PC.

TRANSPORTE

Preferência inicial:
WebSocket TLS para sessão bidirecional persistente.

Fallback futuro:
HTTP streaming/long-poll se houver necessidade real.

Não criar fallback antes de medir necessidade.

HANDSHAKE

Conceitualmente:
1. desktop autentica device;
2. backend valida conta + device + revogação;
3. relaySessionId efêmero é criado;
4. servidor envia challenge;
5. device prova posse da credential;
6. conexão fica ready;
7. heartbeat mantém presence.

Estados:
- offline;
- connecting;
- authenticating;
- ready;
- reconnecting;
- revoked;
- error.

RECONNECT

Exponential backoff com jitter.
Limite máximo.
Sem busy loop.

Internet caiu:
- editor local continua;
- relay vira offline;
- novas chamadas remotas falham com erro claro;
- não executar fila de writes remotas antigas automaticamente depois de horas sem revalidação.

SEGURANÇA DO RELAY

Relay nunca confia em:
- clientId declarado pelo modelo;
- projectId fornecido pela cloud;
- pluginId arbitrário;
- permission arbitrária.

O desktop revalida tudo.

Envelope remoto precisa ter:
- protocol version;
- requestId;
- account context autenticado pelo servidor;
- target device;
- timestamp;
- expiration/deadline;
- operation type;
- payload bounded;
- idempotency key quando aplicável.

Limites:
- payload máximo;
- requests concorrentes;
- timeout;
- rate limit por account/device/plugin;
- conexão única ou política explícita por device.

REPLAY PROTECTION

Pedidos mutáveis precisam:
- requestId único;
- expiration curta;
- duplicate detection;
- idempotency semantics explícitas.

Não reaplicar write apenas porque a conexão caiu antes do ACK.
